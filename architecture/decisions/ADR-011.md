# ADR-011: Builder stages 1-3 in sequence, stage 4 split into parallel test workers per acceptance-criterion group

**Date:** 2026-11-23
**Status:** Proposed
**Decision area:** D1 Splitting the work
**Supersedes:** ADR-001

## Context

ADR-001 used one builder role for stages 1-4, one call per stage. The maintainers' existing agent (SpecBridge)
splits a ticket by acceptance criterion and runs independent workers in parallel, which keeps each worker's context
small and lets one weak criterion be retried alone. Code changes (stage 3) cannot safely be split that way: several
agents editing the same source files in parallel would conflict. Tests for different criteria can be written
independently.

Options considered:
1. Keep ADR-001 (one builder call per stage)
2. **Stages 1-3 sequential; stage 4 = orchestrator node groups ACs (max 4 groups) and Sends one criterion_worker subgraph per group + one e2e_worker (2+ groups), each in its own git worktree, writing one test file; merge combines them**
3. Parallel workers for stage 3 (implementation) too
4. One worker per single AC (no grouping)

## Decision

We will keep stages 1-3 as single sequential agent calls and split stage 4 into parallel test-worker subgraphs,
one per acceptance-criterion group, plus an e2e/regression worker. Workers see only their own ACs and the src diff,
work in their own worktree, and return a WorkerResult; merge (code) writes the files and runs the full suite.

## Consequences

- Each AC gets a focused tester; an uncovered AC is re-sent alone (no full redo).
- Workers run in parallel (max 3 at a time) so stage 4 is faster.
- More agent calls per run (cost) and Gemini rate limits.
- Tests are written without seeing each other: duplicated fixtures, possible overlap.
- Signal to revisit: workers' tests pass alone but conflict when merged, or cost per run rises without better hidden-test results.
