# ADR-002: Deterministic state machine in code, review loop unrolled into fixed Actions jobs

**Date:** 2026-11-23
**Status:** Proposed
**Decision area:** D2 Control flow

## Context

GitHub Actions job graphs are DAGs: a job cannot loop back to an earlier job. Stage 4 must loop to stage 3 on
failing tests, and the review must loop back at most twice. Someone has to decide when to go back.

Options considered:
1. Fixed linear pipeline with no loops
2. **Python state machine (`orchestrator.py`) inside one build job for stages 1-5; review rounds unrolled as fixed jobs gate→build→review-1→publish-1→rework-1→review-2→publish-2→finalize**
3. LLM planner/orchestrator agent that decides the next stage
4. Separate workflows triggering each other via `workflow_dispatch`/`repository_dispatch` (recursion)

## Decision

We will drive stages 1-5 with a code state machine with explicit retry caps, and write the two review rounds out as
fixed jobs. The orchestrator (code), not an agent, decides every loop-back, using check results and the reviewer's `route` field.

## Consequences

- Loop bounds are visible in the YAML and code; a run cannot loop forever.
- The job graph in the Actions UI matches the stage diagram, so runs are easy to follow.
- Less flexible than an LLM planner: new situations need code changes.
- Signal to revisit: the fixed retry policy goes back to the wrong stage often.
