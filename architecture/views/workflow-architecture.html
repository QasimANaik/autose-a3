AutoSE workflow: from labelled issue to reviewed pull request

A maintainer labels an issue autose (or comments /autose). Builder agents write the spec, design, code and tests in a fresh context for each stage. Plain code checks every stage and opens the pull request. A separate reviewer agent in a read-only job reviews it. A person decides whether to merge.

builder agent (Gemini Flash) reviewer agent (Gemini Pro) deterministic code, no LLM human decision

1 · The Actions job graph

GitHub Actions jobs cannot loop, so the two review rounds are separate jobs in a fixed graph. Each box shows the token permissions that job gets; the workflow default is permissions: {}.

2 · Inside the build job: stages, checks and loop-backs

orchestrator.py is a state machine. Each stage is a new gemini -p call that only gets the artifacts it needs. After every call, code runs the check, reverts files the stage was not allowed to touch, and decides what runs next.

3 · Who holds what

Credentials and tools differ by component. An agent never receives a GitHub token, so even if the issue text hijacks it, it cannot push, comment or approve.
