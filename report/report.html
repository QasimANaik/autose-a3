1. Architecture

A maintainer who is OWNER, MEMBER or COLLABORATOR labels an issue autose or comments /autose. A gate job (no secrets, no model) accepts the trigger. The build job then runs a LangGraph StateGraph whose nodes are the six fixed stages:

  • Each agent node is one fresh headless gemini -p call. It gets only the artifacts it needs and has a role-specific tool policy.
  • Every check and every route is plain Python. No model decides whether a stage passed or where the run goes next.
  • Stage 4 fans out with Send to parallel test workers, one per acceptance-criterion group, each in its own git worktree, plus one e2e/regression worker.
  • The review is a second, small LangGraph graph in its own job with a read-only token. It never receives the builder's artifacts.
  • If changes are requested, the job graph runs the main graph once more (rework-1) and then review-2. That is at most two rounds, and the bot never merges.

2.1 The three decisions that mattered most

(1) Every check and route is code, not a model (ADR-007, ADR-012). Each failed run stopped at a precise place with a reason in its artifact, and each became a concrete, testable fix (Table 3). The same runs exposed the cost of this decision. A code check is only as good as its rules, and most failures were caused by our own checks or routes, not by bad agent code:

  • a model outage scored as a spec failure (run 3);
  • ruff . blaming the implementer for the workers' files (run 4);
  • no route for "the test is wrong" (run 6);
  • a parser rejecting (new) inside backticks (run 7) and a backticked None (run 12);
  • no way to change existing tests (run 11);
  • a CI failure routed to the implementer when a generated test was at fault (run 16).
In three of those runs (6, 11 and 16) the agent's code was already correct: the hidden tests pass 4/4. Each check needs a clear owner, meaning the stage that is able to fix what it checks.

(2) Role separation enforced in code, with parallel test workers (ADR-005, ADR-011, ADR-015). The implementer may change only src/ and each worker only its own test file. Everything else is reverted after the call:

  • run 4: tests/fixtures/math.txt and two generated tests reverted;
  • runs 12 and 16: tests/fixtures/url.txt reverted.
So an agent never weakened a test to pass. Strict separation also blocked a legitimate behaviour change (issue #1, run 11). ADR-015 opened a narrow, traceable path: the design declares the fixture file and cites the AC that requires the change. In the re-run (run 14) the design declared tests/fixtures/table.txt, only that file changed, and the PR passed CI, review and 4/4 hidden tests. One worker per AC group kept contexts at 0.25–0.75M tokens per worker. When a worker tested a wrong AC (run 6), loop_dispute re-checks just those test files.

(3) One cheap model everywhere, with independence carried by the job (ADR-014, ADR-008). A 429, a retired fallback and the price list moved the design from Flash + Pro to gemini-3.5-flash-lite everywhere. A successful issue costs $0.21–$0.39 and takes 8–10 minutes. Because the reviewer shares the builder's model, its independence rests on things a model cannot override:

  • its own job with a read-only token;
  • no builder artifacts, transcripts or PR body;
  • its own adversarial checklist;
  • a code judge that enforces the evidence rule.
On the five seeded PRs, this same-model reviewer gave the expected verdict 5/5:
  • the incomplete fix;
  • a javascript: sanitisation bypass, flagged as a blocker;
  • tests that assert nothing;
  • a wrong-layer fix, routed as approach;
  • a clean PR, approved.
In each case it ran the issue's example and the suite itself. Correlated blind spots remain possible, but on this sample the job-level separation was enough.

What the reviewer caught, and where it was wrong. On the bot's own PRs it gave four approvals, all correct according to the hidden tests and CI. On the seeded PRs it caught all four planted defects, each with file:line evidence and a probe it ran itself, with the right severity and route:

  • nested <ul> (major);
  • the sanitize_url bypass (blocker);
  • tests with no assertions (major);
  • the wrong layer plus the unfixed parentheses case (blocker, route approach).
It also approved the clean PR. There were no false approvals or rejections, and the judge discarded no findings. It had two weak spots:
  • For PR #17 it accepted the updated fixture expectations with only the general remark "fixtures are correctly updated".
  • It runs tests on CPython only, so it cannot see PyPy-only failures (runs 16 and 17 were stopped earlier, by the CI gate).
Review cost $0.013–$0.35 per round. The 1.3M-token sp-3 review explored the fixture changes in depth.

Cost and time. In total: 114 agent calls, 44.0M input tokens (79% cached), 264k output, $4.73. A successful issue costs $0.21–$0.39 (mean $0.30) and takes 8.3–10.2 min from comment to posted review. A seeded review costs $0.01–$0.35 and takes about 2 min. Failed or cancelled issue runs cost $3.10, two thirds of the total, mostly on loop-backs that could not succeed.

5. Hindsight

If I started again tomorrow, the first decision I would change is how failures are classified and who owns each check (ADR-007, ADR-009). I would write the failure taxonomy before writing any check: provider down, check wrong, requirement wrong, test wrong, code wrong, environment-specific. Each class would map to exactly one stage that can fix it. In this project that knowledge arrived one failed run at a time (Table 3). In three of the failed runs the code was already correct (hidden tests 4/4), and two thirds of the money went on runs that looped a stage that could not fix the problem. The latest example: in runs 16 and 17 generated performance tests failed only on PyPy CI, and the CI failure was routed to the implementer. A second change, close behind: write the tests from the spec before the implementation, and keep tooling and performance requirements (mypy, benchmarks, wall-clock limits) out of the acceptance criteria.

6. Limitations and threats to validity

  1. Small sample, no repetitions. Five issues, one run each on the final workflow, five seeded PRs, one review per PR. LLM output is not deterministic. Stage rates rest on 4–12 observations.
  2. The system changed between runs. PRs #7–#15 and a model change landed during the runs, so the stage rates mix several versions of the workflow.
  3. Author bias and issue selection. One person wrote the issues, the hidden tests, the seeded defects and the workflow. The original vague issue (#5, inline math) was closed and replaced by #18 after three failed runs, which favours the pipeline (its text and hidden tests are kept in experiment/issues/replaced/ and experiment/hidden_tests/replaced/). Issue #1 turned out to be a behaviour change that contradicts upstream's fixtures. The seeded defects are plausible, but only four of them.
  4. Same model for builder and reviewer (ADR-014), and E1's weak arm is missing (credits ran out). So the 5/5 detection result cannot yet be attributed to the prompt and permissions rather than to the model.
  5. Hidden tests are narrow (4 per issue, written by the author), and CI differs from the local checks (PyPy). Passing hidden tests does not make a PR mergeable as is; merging is left to a human.
  6. Costs are list prices applied to the usage files (gemini-3.5-flash-lite $0.30 / $0.03 / $2.50 per 1M). Implicit-cache hit rates varied (66–86%).
  7. Paths tested only locally. Resume from checkpoint, the dispute route and the draft-PR hand-off were verified by local replays with a faked model, not in a real Actions run.
