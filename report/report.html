1. Architecture

A maintainer who is OWNER, MEMBER or COLLABORATOR labels an issue autose or comments /autose. A gate job (no secrets, no model) accepts the trigger. The build job then runs a LangGraph StateGraph whose nodes are the six fixed stages:

  • Each agent node is one fresh headless gemini -p call. It gets only the artifacts it needs and has a role-specific tool policy.
  • Every check and every route is plain Python. No model decides whether a stage passed or where the run goes next.
  • Stage 4 fans out with Send to parallel test workers, one per acceptance-criterion group, each in its own git worktree, plus one e2e/regression worker.
  • The review is a second, small LangGraph graph in its own job with a read-only token. It never receives the builder's artifacts.
  • If changes are requested, the job graph runs the main graph once more (rework-1) and then review-2. That is at most two rounds, and the bot never merges.

2.1 The three decisions that mattered most

(1) Every check and route is code, not a model (ADR-007, ADR-012). Each failed run stopped at a precise place with a reason in the stage's artifact. That turned every failure into a concrete fix: run 3 → PR #7, run 4 → PR #7, run 6 → PR #9, run 7 → PR #10. The same runs also exposed the cost of this decision. A code check is only as good as its rules. Four of the five failed runs were stopped by our own checks or routes, not by bad agent output:

  • a model outage counted as a spec failure (run 3);
  • ruff . blamed the implementer for the workers' files (run 4);
  • no route existed for "the test is wrong" (run 6);
  • a parser rejected (new) inside backticks (run 7).
Deterministic checks are cheap and reproducible, but each one needs a clear owner: which stage may fix what it checks.

(2) Role separation enforced in code, with parallel test workers (ADR-005, ADR-011). The implementer may only change src/ and the workers only their own test file. Everything else is reverted after the call. In run 4 this stopped the implementer from editing tests/fixtures/math.txt and two generated tests to make failing tests pass. Splitting stage 4 into one worker per acceptance-criterion group kept each context small: 230–340k tokens per worker in run 8. The cost of separation showed in run 6: a worker faithfully tested a wrong acceptance criterion, and the implementer could not touch tests. That needed a new route, loop_dispute: when only new tests fail and the implementer keeps its code, exactly those test files are re-checked once, and a persisting disagreement goes to a human.

(3) One cheap model everywhere, with independence carried by the job (ADR-014, ADR-008). Price data and two failed model calls (a 429 and a retired fallback) moved the design from Flash + Pro to gemini-3.5-flash-lite everywhere. The complete run cost $0.21. Because the assignment does not require a different reviewer model, the reviewer's independence now rests on things a model cannot override:

  • its own job with a read-only token;
  • no builder artifacts, transcripts or PR body;
  • its own adversarial prompt;
  • a code judge that drops findings without evidence and rejects an "approve" that lists no checks.
The open risk is correlated blind spots between builder and reviewer. Experiment E1 and the seeded PRs exist to measure it.

5. Hindsight

If I started again tomorrow, the first decision I would change is how failures are classified (ADR-007 and ADR-009). I would design the failure taxonomy before the checks. Every stop should say whose fault it is (provider, our check, the test, the code, the requirement) and which stage owns the fix. In this project that knowledge arrived one failed run at a time: outage vs spec failure (PR #7), check scope vs stage permissions (PR #7), "the test is wrong" (PR #9), format strictness (PR #10). Each fix was small, but each cost a full run. A second change, close behind: write the tests before the implementation, from the spec. A wrong acceptance criterion (run 6) would then surface before any code exists, rather than as an implement/test disagreement at the end.

6. Limitations and threats to validity

  1. Very small sample. One complete run, one issue fully resolved, one review. Pass rates per stage rest on 1–5 observations and no repetitions. LLM output is not deterministic, so the same issue can pass or fail on a re-run.
  2. The system changed between runs. PRs #7–#10 and a model change landed between runs 3 and 8, so the runs are a development history, not trials of one fixed system. Stage pass rates mix several versions.
  3. Author bias. The same person wrote the issues, the hidden tests, the seeded defects and the workflow. The issues were chosen to be solvable in one or two files of a small, well-tested library, which favours the pipeline. Results may not transfer to larger or less tested repositories.
  4. Same model for builder and reviewer (ADR-014). Errors may be correlated. The reviewer's single approval so far says nothing about its ability to catch defects, which E1 still has to measure.
  5. Cost figures use Gemini paid-tier list prices (gemini-3.5-flash-lite $0.30 / $0.03 / $2.50 per 1M tokens) applied to the usage files. Free-tier calls were not actually billed, and implicit-cache hit rates (69–82%) vary between runs.
  6. Untested safety paths. Resuming from a checkpoint, the dispute route and the prompt-injection defences were tested with local simulations (faked model and GitHub), not yet in a real Actions run. Injection was only observed as flagged phrases in a simulated issue.
